# Deviation allowlist of the firmware port (format: emulator/emu/allowlist.py), used by the differential harness
# (emulator/diff/compare.py, scenarios of emulator/diff/scenarios) and by the hardware-safety monitor
# (emulator/emu/safety.py, safety_* entries).  References: firmware/DESIGN.md section 10.

# HW-04: the GPIO output level is written before MODER, so the port drives PD1 and PE9 from "not driven" straight to 1
# where v2.05 first drives them to 0 (0x0801C08A, 0x0801C0C2) and then to 1 (0x0801C094, 0x0801C0CE).  Cold boot and
# wake from STOP (firmware/requests/W1_to_W10.md item 3).  The wake step "PD1 Z -> 1 with PE9=Z,PD1=Z" needs no entry:
# v2.05 makes it itself at wake (GPIO_Init at 0x0801BD86 with the PD1 output bit already set; whitelist 'power' line).
HW-04  safety_power  *  pins == PD1 and old == Z and new == 1 and ctx == PE9=1,PD1=Z
HW-04  safety_power  *  pins == PE9 and old == Z and new == 1 and ctx == PE9=Z,PD1=1

# OF-08: calibration-mode entry (MODE at power-on, then REL) does not rewrite the six user-zero records 0x4D0..0x4FC;
# v2.05 writes A5 00 00 00 00 to each (analysis/keys_setup.md 3.1, 5.2).  The scenario's assertions on those bytes
# (lines 12..17) describe v2.05.
OF-08  eeprom        poweron_calmode_erase  offset in 0x4D0..0x4FF
OF-08  eeprom_final  poweron_calmode_erase  offset in 0x4D0..0x4FF
OF-08  assert        poweron_calmode_erase  line in 12..17

# OF-23: the DIODE 3 V / 15 V selection is not written to EEPROM 0x12 (v2.05: FUN_080159C8 writes it, boot forces 3 V).
# diode_range line 15 asserts the v2.05 write.
OF-23  eeprom        *           offset == 0x12
OF-23  eeprom_final  *           offset == 0x12
OF-23  assert        diode_range line == 15

# OF-12: cal.bin is a 1248-byte file that also holds the user-zero records 0x4D0..0x4FF (DESIGN.md section 10, 7.3);
# v2.05 writes 1200 bytes, EEPROM 0x000..0x4AF (calbin_save 0x0801CD14, analysis/keys_setup.md 3.2).  The card traffic
# of the save differs with the file size; calbin_save line 14 asserts 1200.
OF-12  sd_files      calbin_save  path == /CAL.BIN
OF-12  sd_block      calbin_save  any
OF-12  sd_cmd        calbin_save  any
OF-12  assert        calbin_save  line == 14

# OF-17: PEAK while the 1 kHz filter is on is refused (refusal beep, no state change); v2.05 accepts it and the main
# display goes blank.  In peak_with_filter_of17 the PEAK press starts at 12.0 s (dial at 0; wait 3; MODE press 0.5 s;
# wait 2; wait 3; long REL 1.5 s; wait 2): from there the display, the HY3131 configuration and the buzzer differ.
OF-17  lcd           peak_with_filter_of17  t in 12.0..1000.0
OF-17  spi           peak_with_filter_of17  t in 12.0..1000.0
OF-17  gpio          peak_with_filter_of17  t in 12.0..1000.0
OF-17  lcd_final     peak_with_filter_of17  any

# OF-11: the first status frame after the BLE transfer is switched on is built before it is sent (v2.05 can send the
# previous buffer, analysis/ble_packet.md section 2).  In the BLE scenarios the long PEAK press starts at 3.0 s and the
# transfer starts when the long press fires (50 ticks), the first frame within the next 50 ticks: window 3.0..4.5 s.
OF-11  uart_tx       ble_*  t in 3.0..4.5

# OF-10: command echoes are queued between status frames instead of being sent at once into a running frame.  The
# injected frame of ble_key_injection and ble_set_clock arrives at 5.5 s; the echo and the frame around it fall within
# 5.5..6.6 s (one 50-tick frame period plus an echo of 5 or 15 bytes at 19200 baud).  ble_bad_key_frame has no entry:
# its key pairs differ, so v2.05 sends no echo (analysis/ble_packet.md section 6).
OF-10  uart_tx       ble_key_injection  t in 5.5..6.6
OF-10  uart_tx       ble_set_clock      t in 5.5..6.6

# HW-04 (board_gpio_init, firmware/src/brd/board.s 55..130; DESIGN 4.2, 10): the port writes each pin's output level before
# MODER and configures the pins port by port, v2.05 writes MODER first (every pin first drives 0, then its level) and
# interleaves the ports.  Cold boot, power cycle and MCU reset: in the gpio stream the pins that end at 1 (PD0 PD1 PD7
# PC11 PF4 PF5 PA12) lose their transient 0 and the whole burst comes in another order (PE15 and backlight swap).
# The burst is the application's GPIO set-up 0.035..0.037 s after power-on (the bootloader's own pin events at 0.002 s
# are identical).  Pins of the burst whose events are identical and in order (ble_supply PH2 PA11 PF8) stay compared.
HW-04  gpio   *  pin ~ "PD[017]" and boot in 0.03..0.045
HW-04  gpio   *  pin == PE15 and boot in 0.03..0.045
HW-04  gpio   *  pin == backlight and boot in 0.03..0.045
HW-04  gpio   *  pin == PC11 and boot in 0.03..0.045
HW-04  gpio   *  pin ~ "PF[45]" and boot in 0.03..0.045
HW-04  gpio   *  pin == PA12 and boot in 0.03..0.045
HW-04  power  *  pin == PD1 and boot in 0.03..0.045

# HW-06 (firmware/src/brd/frontend.s 635): leaving the DIODE 15 V source the port writes PF6 low first, then PE15 high;
# v2.05 writes PE15 high first (3 instructions before PF6 low).  diode_range: the second RANGE press (line 13) leaves 15 V.
HW-06  gpio   diode_range  step == 13 and pin == PE15 and level == 1
HW-06  gpio   diode_range  step == 13 and pin == PF6 and level == 0

# OF-14 + OF-15 (ORIGINAL_FIRMWARE_ISSUES.md): a negative DC reading is decoded 1 LSB high (OF-14) and rounded toward zero
# (OF-15), so v2.05 shows -1.2344 for -1.2345 V and -47.999 for -48.0 V, the port the exact value; the intermediate
# frames of the mean that straddles the step carry a negative value too.  Every LCD event whose main display is
# negative, after the start-up phase (the lamp test at power-on draws "-8.8.8.8.8").
OF-14+OF-15  lcd  dc*_values  main ~ "-*" and boot in 0.5..1e9
OF-14+OF-15  lcd  ua_values   main ~ "-*" and boot in 0.5..1e9

OF-14+OF-15  lcd_final  lowz_values  main ~ "-*"
# AC+DC with a negative DC component (acdc_values line 12: dc=-2.0): the combined value is built from the DC phase, so the
# steady reading differs in the last digit (v2.05 2.2359, port 2.2360); OF-28 (shared smoothing state) acts on the same
# value.
OF-14+OF-15+OF-28  lcd  acdc_values  step == 12 and main ~ "2.2*"

# OF-21 (FUN_08018AD8, 0x08018AF4..0x08018B0C): the board temperature on the secondary display is rounded on the wrong digit
# in v2.05 (boot_v: v2.05 shows 27.0, the port 27.1 for the same ADC value).  Persistent in every frame that shows it, so the secondary
# display is not compared while it shows a temperature; the main display and the annunciators are.
OF-21  mask:lcd:sub  *  sub ~ "*c"
# The same rounding on the main display in TEMP mode and OF-24 (cold-junction value kept below -20.0 degC in v2.05, the
# existing fault path in the port; temp_values line 19 drives the board to -22 degC): the main display is not compared in
# the TEMP steps (lines 11..19).
OF-21  mask:lcd:main  temp_values  step in 11..17
OF-21+OF-24  mask:lcd:main  temp_values  step == 19
OF-21+OF-24  lcd_final  temp_values  main ~ "-*"
# BLE frames carry the same temperature: sub value low byte (pos 12) and the checksum (pos 18, XOR of the other bytes,
# analysis/ble_packet.md sections 3 and 5) differ by the 0.1 degC.
OF-21  uart_tx  ble_*  pos == 12
OF-21  uart_tx  ble_*  pos == 18

# OF-18 (FUN_0800B6D4 / 0x0800B080): the pulse width is computed from a duty truncated to 0.1 % in v2.05 (1 kHz, 25 %
# shows 0.2499 ms) and from the counts in the port (0.2500 ms).  freq_values: PULSE mode from line 13 (MODE press) to
# the DUTY mode of line 17; the first DUTY frame still shows the width in the new unit (0249.9 / 0250.0).
OF-18  lcd  freq_values  step in 13..17 and main ~ "0*"

# OF-33 (cap.s 474): the CAP timeout range jump draws the old count with the new decimal point for one update in v2.05;
# the port blanks across the jump.  cap_values: the jumps made by the inputs of lines 14 (1.0000) and 16 (9999).  The

OF-33  lcd  cap_values  step == 14 and since in 0.9..1.1 and main == "1.0000"
OF-33  lcd  cap_values  step == 16 and since in 1.7..2.0 and main ~ "*9999"

# IMP-05 (analysis/autorange_and_scheduler.md section 9): setup item 10 in BEEP steps REL through DN 1 .. UP300 (16 codes)

# OPT-01 + OPT-08 (DESIGN 11; src/cal/cache.s, nvm_read_block): start-up differs in time.  Measured on boot_v: the application's
# GPIO burst comes 0.54 ms earlier (RAM init by copy instead of lz77, OPT-01), the first HY3131 write 1.24 ms later (the
# 1280-byte calibration cache is loaded before it, OPT-08: +1.78 ms).  The LCD-paced baseline loop then runs 1.07..1.24 ms
# later than v2.05's, so an event that the main loop produces falls one LCD frame (13.84 ms, 72 Hz) later or earlier when
# its trigger lies near a pass boundary: measured differences of lcd and gpio events in the 93 baseline runs cluster at
# +1.1, +14.9 and -12.8 ms.  Tolerance = one frame + the shift + 0.4 ms.
OPT-01+OPT-08  tolerance:lcd    *  0.0155
OPT-01+OPT-08  tolerance:gpio   *  0.0155
OPT-01+OPT-08  tolerance:power  *  0.0155

# NF-11 (DESIGN 3.4, 6.7): the time page (setup page 7) is drawn by the main loop on a request of the TIM2 handler, v2.05
# draws from the handler.  The blinking separator and the page changes reach the glass up to three LCD frames later
# (measured: 42.6 ms, setup_time / setup_navigate_dcv, 3 x 13.84 ms + 1.1 ms).
NF-11  tolerance:lcd  setup_time          0.045
NF-11  tolerance:lcd  setup_navigate_dcv  0.045

# OPT-03 (nvm/flash.s 272..294): an EEPROM byte that already holds the value is not programmed again, so the changed byte
# of a restore is committed earlier.  calbin_load: v2.05 writes the 17 bytes 0x000..0x010 before the changed byte 0x010
# at 2 x 3.28 ms each (emu/periph/flash.py TPROG_US_DEFAULT = 3280): 111 ms at most (measured: 92 ms earlier).
OPT-03  tolerance:eeprom  calbin_load  0.115
